# IB Event Manager

IB Event Manager는 IB(자사)의 행사 일정을 구글 캘린더와 연동하여 모바일 환경에서 보다 쉽게 일정을 확인할 수 있도록 하는 것을 목적으로 한 프로젝트 입니다.

## 1. 개요

- **문제 인식**:
  - 기존 행사 일정 프로그램(웹사이트 형태로 제공)은 일정 확인 시 반복적인 로그인 과정이 필요하다는 점, 모바일 환경에서는 사용이 불편하다는 점(UI 가독성 미흡)으로 인해 신속한 일정 확인에 제약이 있습니다.
  - 행사 일정 취소, 세부 내역 변경 시 이에 대한 알림 기능이 없어 부서 간 정보 불일치로 인한 업무 혼선(고객 컴플레인 발생 등)이 종종 발생합니다.
- **해결 전략**:
  - 주기적으로 행사 일정 스크랩 및 전처리, 구글 캘린더 등록 과정을 수행하여 캘린더 앱을 통해 행사 일정을 빠르게 확인할 수 있는 환경을 조성합니다.
  - AWS Lambda + CloudWatch Event를 활용하여 15분 간격으로 일정을 업데이하도록 환경을 조성합니다.
  - 일정 최신화에 따른 전후 변동사항 파악을 위해 기존 데이터를 Redis(Upstash)에 보관하여 최신 데이터와의 비교를 통한 변동사항을 체크합니다.
  - 내용 변경 시 Slack으로 알림메시지를 전송하여 변동 사항을 빠르게 인지할 수 있습니다.
- **서버리스 환경 검토 사항**
  - **환경 설정의 1순위 고려 사항은 비용입니다.**
  - 비용 측면 고려: 스크래핑과 동기화를 짧은 러닝타임으로 처리해 비용을 최소화하기 위해 프로비저닝 방식(EC2)이 아닌 서버리스(Lambda) 방식을 채택했습니다.
  - Redis 사용 이유: 현재 DB는 월 평균 250~500건의 일정을 수집, 관리하며 일정 변동 사항 확인용으로만 사용하기에 속도에 중점을 둔 Redis의 Hash 방식를 채택하였으며 HSET과 HMGET을 적용하여 하루 약 90건의 커멘드만 고정적으로 발생하도록 하여 Upstash의 한달 무료 한도인 500k를 넘지 않도록 설계했습니다. 이후 수집량 증가, 장기 데이터 저장 요구, 데이터 분석 등에 활용될 경우 영속성을 고려하여 MongoDB와 같은 NoSQL로 변동할 계획입니다.
  - 인프라 활용: CloudWatch, SNS 기능을 적용하여 모니터링 및 오류 시 알람 기능을 쉽게 적용할 수 있습니다.

## 2. 동작 흐름

1. **Lambda 트리거**  
   CloudWatch Event 규칙이 15분 간격으로 Lambda 핸들러 함수를 호출하고, 입력 파라미터를 지정하지 않을 경우 현재 시각을 기준으로 디폴트 수집 기간을 설정합니다.

2. **오케스트레이션 & 모니터링**  
   `scrapeOrchestrator`가 로그인 → 스케줄 수집 → 데이터 비교 → 구글 캘린더 동기화 → Slack 알림까지 전 단계를 실행하며 단계별 진행상황을 로깅, 리포트 형태로 수집합니다.

3. **세션 확보 & 스크래핑**
   - Puppeteer Core + Sparticuz Chromium 패키지를 통해 로컬 뿐 아니라 Lambda 환경에서도 기존 일정 관리 페이지에 접속, 로그인하고 세션 쿠키 확보가 가능하도록 합니다.

4. **데이터 정규화 & 비교**
   - 파싱된 일정은 Map 구조로 정규화되어 관리합니다. (최초 데이터 저장 및 수정을 로컬에서 수행하도록 계획하면서 Map 기준으로 로직 작성)
   - 이전 수집 데이터는 Redis에서 불러오며, 신규 일정 등록 및 변경사항 확인에 사용됩니다.

5. **캘린더 동기화 & 알림**
   - Google Calendar Batch API로 신규/변경/삭제 요청을 한 번에 보내고, 응답을 Redis에 저장하여 동기화 합니다.
   - 일정 변동 사항은 Slack 채널로 요약 전송되어 협업자가 즉시 인지할 수 있습니다.

6. **리포트 & 에러 핸들링**
   - `ReportCollector`가 각 단계의 소요시간을 측정하고 등록된 예외 발생 시 Slack으로 오류를 전달합니다.
   - 로그인 시 Timeout 등 일시 오류는 `requestRetry`로 3회까지 재시도하여 안정성을 높였습니다.

## 3. 환경 설정 & 로컬 개발

1. **요구 사항**
   - Node.js 22.x (esbuild 번들 타깃과 동일)
   - yarn (선택) 또는 npm

2. **환경 변수**
   - `.env` 파일을 `.env.example`을 참고해 작성합니다.
   - `env.ts`의 Zod 스키마가 필수 값을 검증하므로, Google/Slack/Redis/WINGS 관련 필수 값을 모두 채워야 정상 실행됩니다.

3. **의존성 설치 & 실행**
   ```bash
   yarn install
   yarn dev            # ts-node로 로컬 실행
   yarn build          # tsc 컴파일
   yarn build:lambda   # 번들 파일 생성
   yarn start          # dist/index.js 실행
   ```

## 4. AWS Lambda 배포 가이드

1. **번들 생성**
   - `yarn build:lambda`로 esbuild 번들을 생성합니다. 이때 Puppeteer와 @sparticuz/chromium은 Lambda환경에서도 실행 가능하도록 별도 패키지로 함께 전달되어야 하므로 external 처리합니다.

2. **런타임 패키징**
   - `lambda_pkg/` 디렉터리를 만들고 그 안에 `dist/` 폴더를 준비합니다.
   - 아래와 같은 `lambda_pkg/package.json`을 생성합니다.
     ```json
     {
       "name": "lambda_pkg",
       "private": true,
       "dependencies": {
         "puppeteer-core": "24.34.0",
         "@sparticuz/chromium": "143.0.4"
       }
     }
     ```
   - `cd lambda_pkg && yarn install --production`.
   - 루트 `dist/index.js` (esbuild 결과물)을 `lambda_pkg/dist/`로 복사합니다.
   - `zip -r ../lambda.zip .`으로 `lambda_pkg` 전체를 압축합니다.

3. **S3 업로드 & Lambda 갱신**
   - 생성된 `lambda.zip`을 S3에 업로드하고, Lambda 함수 코드 소스로 지정합니다.
   - 런타임은 Node.js 22.x, 핸들러는 `dist/index.handler`로 설정합니다.
   - CloudWatch Event 규칙(15분 간격)을 연결해 자동 실행을 구성합니다.

## 5. 주요 구현 포인트

| 영역                           | 설명                                                                                                                                                                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Lambda에서의 Chromium 사용** | Lambda 환경에서 로그인을 통한 세션 쿠키 확보 시 Chromium 바이너리가 정상 실행되도록 Puppeteer Core + Sparticuz Chromium 패키지를 zip 파일에 포함시켜 배포합니다. 해당 패키지는 번들 파일에 포함 시 실행이 불가했기 때문입니다. |
| **병렬 스크래핑 & 파싱**       | 월별 일정 수집 API 요청 시 병렬(동시성) 호출하고, 호출 수가 많은 경우 `p-limit`로 제어하여 하나씩 순차 요청/응답으로 인한 지연을 방지합니다.                                                                                   |
| **Google Calendar 배치 처리**  | 구글 캘린더 Batch API 방식 (multipart/mixed)을 적용하여 하나의 요청 안에 최대 1,000건의 독립적인 HTTP 요청을 묶어서 수행합니다. 그래서 수백 건의 일정 등록 시 요청/응답 비용을 최소화합니다.                                   |
| **Slack 실시간 알림**          | 일정의 신규/변경 이벤트 발생 시 Block 메시지로 요약해 슬랙 채널에 전송하고, 오류 발생 시 스택 트레이스를 포함한 경고를 함께 전송하여 함수 실행 결과에 대한 알림 기능을 제공합니다.                                             |
| **신뢰성 & 관측성**            | `ReportCollector`가 각 함수 수행 단계별 속도, 성공여부 등을 측정하여 Lambda 로그에서 실행 결과를 일목요연하게 확인할 수 있습니다.                                                                                              |
